# Architecture Overview

## Goal

TeamFlow manages projects and the work requested by their stakeholders. Its core flow is: stakeholder submits a suggestion or bug report → project manager reviews it and creates/links developer issues → developer updates issues and logs work → project members receive live updates. Managers can request an activity and time report. The architecture demonstrates secured REST, microservices, RabbitMQ, Kafka, FaaS, WebSockets, load balancing, and containers. Progress is tracked in the [roadmap](../project/roadmap.md) and [rubric checklist](../development/rubric-checklist.md).

## Roles

- **Admin:** manages users, roles, and project membership across the system.
- **Project manager:** creates projects, manages stakeholder access, triages submissions, creates and assigns issues, and reviews progress and work logs.
- **Stakeholder:** views permitted project progress and submits suggestions or bug reports.
- **Developer:** views assigned issues, changes status, adds comments, and records time worked.

## Main capabilities

1. JWT authentication and role- and project-scoped authorization.
2. Project and membership management.
3. Stakeholder submissions with type, description, priority suggestion, and attachments metadata.
4. Project-manager triage: accept, reject, request clarification, or create/link one or more issues.
5. Developer issue lifecycle, assignment, comments, and work logs.
6. Real-time project notifications and activity updates.
7. On-demand project activity/time report generated by FaaS.

## Architecture

- Four Spring Boot microservices: user-service, work-management-service, notification-service, and report-service. Each stateful service owns its data; synchronous REST goes through an API gateway.
- RabbitMQ carries report-generation commands. User-issued submission triage and issue creation remain REST calls to their owning services.
- Kafka carries durable submission, issue, work-log, and report facts; notification-service consumes them.
- nginx load-balances stateless API-gateway replicas and proxies authenticated WebSockets to one notification-service instance.
- React + TypeScript shell composes two remotes: stakeholder and team (PM, developer, and admin views).
- Docker Compose is the local demo; Kubernetes/OpenFaaS is the deployment target.

## Main flows

**Triage:** stakeholder → gateway → work-management-service stores the submission → Kafka `submissions.events` → project manager receives notification. PM creates a linked issue through the same service, which validates project membership and publishes `issues.events`.

**Work tracking:** developer updates an assigned issue and records a work log through work-management-service. The service publishes Kafka facts. notification-service consumes relevant events and sends private WebSocket updates.

**Report:** manager requests a report → report-service records a pending request and sends RabbitMQ `reports.generate` → FaaS generates a PDF from a scoped snapshot → report-service records completion and emits `reports.ready`.
